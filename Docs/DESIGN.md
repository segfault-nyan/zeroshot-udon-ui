# ZeroShot Udon UI 設計素案

- 版：0.30（素案）
- 作成日：2026-10-11
- 状態：未承認。この文書の内容はすべて提案であり、承認された項目から実装に進む。

## 1. 目的

VRChat ワールドに、統一感のある UI を短時間で組み込めるようにする。
ワールド制作者は、プレハブを置いて設定するだけで UI を使える状態を目指す。

**コンセプト**

- 既製品（フォント、アイコン集など）を除き、100% AI 生成である。既製品の同梱は認める。
- VRChat の AI 生成ワールドでよく目にする存在になる。

AI 生成ワールドでは、UI を組み込む作業も AI が行う。AI は Unity の画面を操作できないため、コードから UI を組み立てられること（EDT-05）と、AI が読むための利用ガイド（DST-05）を用意する。

## 2. ID の運用ルール

- 各項目に `分類-連番` の ID を振る（例：`CMP-01`）。
- ID は一度振ったら変更しない。削除した項目の番号は再利用せず、状態を「廃止」にする。
- 実装やコミット、やりとりではこの ID で項目を指す。

| 分類 | 意味 |
|---|---|
| FND | 基盤（見た目の土台、共通ルール） |
| CMP | 部品（ボタンなど単体の操作要素） |
| LAY | 容れ物と配置（パネル、タブなど） |
| SYS | 動作の仕組み（イベント、アニメーション、同期など） |
| EDT | エディタ拡張（Unity 上の制作支援） |
| DST | 配布とドキュメント |
| NFR | 品質の基準（性能、互換性など） |
| Q | 未決事項（判断が必要なもの） |

**優先度**
- P1：最初の版に必要。これが揃えば基本的な UI を作れる。
- P2：次の版で追加する。
- P3：余力があれば検討する。

**状態**
- 未着手／試作済（サンプルで形になっている）／実装中／完了／廃止

## 3. 前提となる制約

設計はすべて次の制約の上に成り立つ。

- UI は uGUI と TextMeshPro で作る。Unity 標準の「UI Toolkit」は VRChat ワールドでは動かない。
- スクリプトは UdonSharp で書く。通常の C# より使える機能が少ない。
- UI のボタンなどから直接呼び出せる処理は限られる。そのため、操作の通知は Udon のイベント送信（`SendCustomEvent`）を経由する。
- 設定用のデータアセット（ScriptableObject）は、Udon からは実行時に読めない。そのため、テーマなどの設定は Unity エディタ上でプレハブやマテリアルに書き込む方式にする。
- Canvas は Default レイヤーに置く。UI レイヤーに置くと、VRChat のメニューを開いている間しか操作できない。

対応プラットフォームを PC と Quest（Android）に決めたこと（Q-01）により、次の制約が加わる。

- Quest は半透明の重ね描きに弱い。UI は全体が半透明なので、重ねる層の数を抑える。
- Quest ではポストプロセスが使えない。発光などの効果はシェーダーで描き、控えめにする。
- 背景をぼかす表現（すりガラス風）は Quest では重すぎるため採用しない。
- Android 用ワールドには容量上限（100MB）がある。フォントなど容量の大きい素材は絞り込む。
- Android 用ビルドはスマホでも使われ、タッチ操作にはホバーがない。ホバーしないと分からない UI は作らない。

## 4. デザインコンセプト

サンプルパネルで確認した見た目を基準にする。

**方針**
- 暗い背景に、アクセント色を1色だけ使う。VR で眩しくならないことを優先する。
- 形は角丸とピル形状（両端が半円）で統一する。
- 画像素材に頼らず、形はシェーダーで描く。拡大しても輪郭がぼやけない。

**基準値**（Canvas の 1 単位 = 1mm）

| 項目 | 値 |
|---|---|
| パネル背景 | `#171A21`、不透明度 96% |
| パネル枠線 | 白、不透明度 14%、幅 2 |
| アクセント | `#5C8CFF` |
| 操作部の土台（オフ状態など） | `#404554` |
| つまみ | `#F7F7FA` |
| 文字（主） | `#F2F5FA` |
| 文字（補助） | `#9EA8BD` |
| パネルの角丸半径 | 28 |
| 操作部の形 | ピル形状 |
| 文字サイズ | 見出し 36／本文 24／補足 18 |
| ボタンの高さ | 64 |
| 状態による色の変化 | 通常 86%／ホバー 100%／押下 62% の明るさ |

## 6. 段階計画

| 段階 | 目標 | 含む項目 |
|---|---|---|
| 第1段階 | 設定画面を1枚作れる | P1 の全項目（2026-10-11 に完了） |
| 第2段階 | 複数画面の UI を作れ、配布できる | P2 の全項目 |
| 第3段階 | 発展的な機能 | P3 の全項目（採否は個別に判断） |

第1段階の進め方の案は次のとおり。

## 8. フォルダ構成と命名規則（FND-09）

正式名称は Q-06 で次のとおり決定した。

| 種類 | 値 | 使われる場所 |
|---|---|---|
| 名称 | `ZeroShotUdonUI` | フォルダ名、名前空間、シェーダーのメニュー名 |
| 表示名 | ZeroShot Udon UI | Unity のメニュー、配布時の名前 |
| 接頭辞 | `ZS` | プレハブとマテリアルのファイル名 |

### 8.1 フォルダ構成

```
Packages/com.helkya.zeroshotudonui/   ツールキット本体（配布するパッケージ）
├─ package.json          パッケージの定義（名前、版、必要な VRChat SDK の版など）
├─ README.md             導入手順書（DST-02）
├─ LICENSE.md            ライセンス（DST-04）
├─ CHANGELOG.md          版ごとの変更内容
├─ Documentation~/       部品リファレンス（DST-03）と、AI エージェント向け利用ガイド（DST-05）
├─ Runtime/              ワールドに組み込まれるもの
│  ├─ Shaders/           シェーダー
│  ├─ Materials/         マテリアル
│  ├─ Scripts/           UdonSharp スクリプトと、対になる U# アセット
│  ├─ Prefabs/
│  │  ├─ Foundation/     Canvas ベースなど（FND）
│  │  ├─ Components/     部品（CMP）
│  │  └─ Layouts/        容れ物と配置（LAY）
│  ├─ Fonts/             フォント
│  ├─ Icons/             アイコン
│  └─ Audio/             効果音
├─ Editor/               エディタ拡張（ワールドには含まれない）
└─ Samples/              サンプル用スクリプト

Assets/ZeroShotUdonUI/   利用者ごとのファイル（配布物にも git にも含めない）
├─ Settings.json         テーマとフォントの設定の控え（EDT-07）
├─ Fonts/                「フォント設定」で取得したフォントとライセンス文書、追加で収録する文字の指定
└─ Demo/                 メニューから生成したデモシーン

Docs/                    設計書と、公開の手順（配布物には含めない）
.github/                 公開のための自動処理（8.8）
README.md、LICENSE.md    リポジトリのトップに表示する説明と、ライセンス
```

- ツールキット本体は、VCC から導入できる形式（VPM）のパッケージとして `Packages/` に置く（Q-02）。
- VCC でツールキットを更新すると、パッケージのフォルダは丸ごと置き換わる。そのため、利用者ごとのファイルはパッケージの外の `Assets/ZeroShotUdonUI/` に置く。コードでは、前者を `UIBuilder.PackageFolder`、後者を `UIBuilder.UserFolder` で指す。
- `Runtime`・`Editor`・`Samples` には、それぞれアセンブリ定義（スクリプトをコンパイルする区画の定義）を置く。パッケージの中のスクリプトは、これが無いとコンパイルされない。
- `Documentation~` は、Unity が読み込まない決まりのフォルダ（名前の末尾が `~`）。パッケージの文書を置く標準の場所で、`.meta` も要らない。
- 文書は日本語で書く。英語版は、メニューを英語にも対応させるときに、あわせて作る。
- 部品や `UIBuilder` の関数を追加・変更したときは、`README.md`、`Documentation~/Reference.md`、`Documentation~/AIGuide.md`、`CHANGELOG.md` も合わせて直す。
- `Runtime` と `Samples` には、UdonSharp 用の設定アセット（アセンブリ定義と同名の `.asset`）も置く。UdonSharp が区画内のスクリプトを認識するために必要。

### 8.2 命名規則

| 対象 | 規則 | 例 |
|---|---|---|
| ファイル名・フォルダ名 | 英語のパスカルケース。空白と日本語は使わない | `RoundedRect.shader` |
| プレハブ | `ZS_部品名_種類` | `ZS_Button_Primary` |
| マテリアル | `ZS_用途` | `ZS_Panel` |
| スクリプト | クラス名とファイル名を一致させる。名前空間は `ZeroShotUdonUI` | `ToggleSwitch.cs` |
| U# アセット | スクリプトと同名で、同じフォルダに置く | `ToggleSwitch.asset` |
| シェーダーのメニュー名 | `ZeroShotUdonUI/シェーダー名` | `ZeroShotUdonUI/RoundedRect` |
| Unity のメニュー | `Tools/ZeroShot Udon UI/…` に集約する | `Tools/ZeroShot Udon UI/サンプル生成` |
| プレハブ内のオブジェクト名 | 英語。Unity 標準の UI の呼び方に合わせる | `Handle Slide Area` |

- 接頭辞は、利用者のプロジェクトで他のアセットと名前が衝突しないように付ける。
- ファイル名に日本語を使わないのは、配布や Android 用ビルドでの文字化けを避けるため。

### 8.3 ID との対応付け

- スクリプトとシェーダーは、冒頭のコメントに設計 ID を書く（例：`// CMP-03`）。
- プレハブなどコメントを書けないものは、5章の機能一覧の「成果物」列に対応を記録する。

### 8.5 プレハブの作り方

プレハブは手作業で組まず、コード（`Editor/PrefabGenerator.cs`）から生成する。

- 構造や初期値を変えるときは、コードを書き換えて、メニュー `Tools > ZeroShot Udon UI > プレハブを生成` で作り直す。プレハブに手で加えた変更は、作り直すと失われる。
- 作り直しても、シーンに配置済みの UI とのつながりは保たれる（オブジェクト名で対応を取るため。動作確認済み）。プレハブ内のオブジェクト名を変えると、この対応が切れる。
- 同じ理由で、**1 つのプレハブの中に、同じ名前のオブジェクトを置かない。親が違っていても置かない。** Unity は名前だけで対応を取るので、同じ名前が複数あると取り違え、配置済みの UI の設定（文字など）が初期値に戻る。選択ボタン群は、選択肢を `Segment 1`、`Segment 2`、その中の文字を `Label 1`、`Label 2` と連番にしている。他のプレハブを中に含む場合、含まれる側の中のオブジェクトは数えない。
- この対応は、利用者がツールキットを更新したときにも効く。公開済みのプレハブの中のオブジェクト名を変えると、利用者が置いた UI の設定が、更新で初期値に戻る。名前を変えるときは、変更履歴の「更新するときの注意」に書く。
- シーンへの配置は `Editor/UIBuilder.cs` の関数で行う。配置した UI はプレハブとつながったままなので、プレハブを直せば配置済みの UI にも反映される。
- 共通マテリアルは、無い場合だけ初期値で作成する。既にあるマテリアルは書き換えない（9章）。
- 他のプレハブを中に含むプレハブ（例：`ZS_Window` は Canvas・パネル・ラベル・ボタンを含む）は、含まれる側より後に生成する。生成の順番は `PrefabKind` の並び順で決まる。
- 見本のシーン（`Assets/ZeroShotUdonUI/Demo/ZS_Demo.unity`）も、コード（`Editor/DemoSceneBuilder.cs`）から生成する。配布物には含めず、利用者の環境で生成する。メニュー `Tools > ZeroShot Udon UI > デモシーンを生成` で作り直せる。シーンに手で加えた変更は、作り直すと失われる。

### 8.6 パッケージへの移動（DST-01）

ツールキット本体を、`Assets/ZeroShotUdonUI/` からパッケージのフォルダに移動した（2026-10-12）。`.meta` ごと移したので、プレハブなどの参照は変わらない。

| 移動前（`Assets/ZeroShotUdonUI/`） | 移動後 |
|---|---|
| `Runtime/`、`Editor/` | `Packages/com.helkya.zeroshotudonui/` の同名のフォルダ |
| `Samples/SampleController.cs` と `.asset` | `Packages/com.helkya.zeroshotudonui/Samples/` |
| `Samples/ZS_Demo.unity` | `Assets/ZeroShotUdonUI/Demo/ZS_Demo.unity`（git の管理から外した） |
| `Editor/Fonts/` のうち、取得したフォントと追加の文字の指定 | `Assets/ZeroShotUdonUI/Fonts/` |

開発時の注意：

- `package.json` には、作者の連絡先と zip の置き場所を書かない。公開のときに、自動処理が補う（8.8）。
- コードからパッケージの中にアセットを新しく作るときは、`PrefabGenerator.CreateAsset` を使う。パッケージの中には直接作れないため、`Assets/` の下に作ってから移している（UdonSharp 本体と同じ方法）。

### 8.7 設定の保存と復元（EDT-07）

VCC でツールキットを更新すると、パッケージのフォルダは丸ごと配布時の状態に置き換わる。利用者が決めたテーマとフォントが失われないよう、設定の控えを `Assets/ZeroShotUdonUI/Settings.json` に保存し、配布時の状態に戻ったことを検知したら元に戻す。

| 対象 | 控えを保存するとき | 保存する内容 | 元に戻す条件 |
|---|---|---|---|
| テーマ | テーマ設定の画面で値を変えたとき（取り消しと「初期値に戻す」を含む） | 共通マテリアル 5 種類の色・角丸・枠線 | マテリアルが初期値に戻っていて、控えの値と違うとき |
| フォント | フォント設定の画面で「生成」に成功したとき | 元のフォントと画像の大きさ | フォントアセットが空のとき（控えのフォントから生成し直す） |

- 確かめるのは、プロジェクトを開いたときと、アセットが取り込まれたとき（`AutoSetup`）。既にあるファイルの中身だけが変わった場合も検知できるよう、アセットの取り込み後に呼ばれる仕組み（`AssetPostprocessor`）を使う。
- テーマは、マテリアルごとに判定する。初期値でも控えの値でもないマテリアルは、利用者が直接書き換えたものとみなして触らない。
- マテリアルを直接書き換えた値は控えに入らないので、更新すると失われる。色はテーマ設定の画面で変えるよう、導入手順書（DST-02）で案内する。
- テーマ設定の画面を閉じた後に取り消し（Ctrl+Z）で初期値まで戻すと、控えと食い違い、次に確かめたときに控えの値に書き戻される。画面を開いている間の取り消しは、控えにも反映される。
- 追加で収録する文字と、取得したフォントは、もともとパッケージの外にあるので、そのまま残る。
- 「空の状態に戻す」を押した後は、エディタを再起動すると控えのフォントから生成し直される。配布物を作るときは、押した後に再起動せずに作る。

### 8.8 公開の仕組み（DST-01）

GitHub で公開する。手順は `Docs/RELEASE.md` にまとめている。

- GitHub の Actions の `Release` を手動で実行すると、`package.json` の版番号で zip を作り、GitHub のリリースに添付する。続けて、公開済みの全部の版から、VCC が読む一覧（`index.json`）と導入ページを作り、GitHub Pages に公開する。
- zip と一覧を作る処理は、Python のスクリプト（`.github/scripts/release.py`）にまとめている。標準ライブラリだけで動き、手元でも試せる。
- **公開先の URL、GitHub のユーザー名、作者の連絡先は、リポジトリのファイルに書かない。** URL は実行時に組み立て、連絡先はリポジトリの変数（`AUTHOR_EMAIL`）から読む。連絡先は、GitHub が発行する noreply のアドレスだけを受け付ける。
- フォントアセットが空でない場合と、公開済みの版番号をもう一度公開しようとした場合は、エラーで止まる。
- 配布されるのは、git に記録された内容。共通マテリアルは、初期値の状態で記録しておく。
- リポジトリには、`Assets/` の下のファイルを記録しない。VCC が作る最初のシーンにはワールド ID が保存され、SDK 付属の素材や TextMeshPro の基本リソースは再配布の可否を確認していないため。どれも、プロジェクトを開けば作り直される。
- 公開にあたり、git の履歴を作り直した（2026-10-12）。それまでの履歴には、個人のメールアドレスとワールド ID が含まれていたため。以前の履歴は、リポジトリの外にバックアップとして保存している。

## 9. テーマ（FND-04）

### 9.1 方式

色・角丸・枠線を**マテリアル**に持たせる。部品は「アクセント用」「土台用」など、役割ごとの共通マテリアルを使う。

- マテリアルを1つ直せば、それを使う全部品に即座に反映される。
- 実行時のテーマ切り替え（SYS-10）も、マテリアルの値を書き換える同じ仕組みで作れる。
- 角丸と枠線はもともとシェーダー（FND-01）の設定値としてマテリアルにあるため、色も同じ場所に置く。

### 9.2 ルール

- マテリアルは 10 種類程度に抑える（NFR-02）。具体的な一覧は実装時に決める。
- 文字の色とサイズはプレハブ側に持たせる。第1段階ではテーマの対象外とする。
- テーマ適用ツール（EDT-02）は、設定値をマテリアルに書き込む小さな画面とする。

### 9.3 採用しなかった案

| 案 | 採用しなかった理由 |
|---|---|
| テーマ用の設定アセットを作り、全要素に目印を付けてツールで一括反映する | 全要素に目印が必要で、反映し忘れると古い見た目が残る。仕組みが大きい |
| 仕組みを作らず、制作者がプレハブを直接編集する | アクセント色を変えるだけで多数の箇所を直すことになる |

### 9.4 テーマ設定の画面（EDT-02）

メニュー `Tools > ZeroShot Udon UI > テーマ設定` で開く。値を変えると共通マテリアルに書き込まれ、シーン上の UI にその場で反映される。

| 設定項目 | 書き込み先 |
|---|---|
| アクセント色 | `ZS_Accent` の塗り、`ZS_Outline` の枠線 |
| 枠線のみのボタンの線の太さ | `ZS_Outline` の枠線 |
| パネルの色（不透明度を含む） | `ZS_Surface` の塗り |
| パネルの角丸の半径 | `ZS_Surface` の角丸 |
| パネルの枠線の色と太さ | `ZS_Surface` の枠線 |
| 土台の色 | `ZS_Track` の塗り |
| つまみの色 | `ZS_Knob` の塗り |

- 正はマテリアルで、画面は開くたびにマテリアルの現在の値を表示する。変えた値は、ツールキットを更新しても元に戻せるよう、パッケージの外にも控えを保存する（8.7）。
- アクセント色は2つのマテリアルで使うため、色を変えるときはマテリアルを個別に直さず、この画面を使う。
- 「初期値に戻す」で、全項目を生成時の値に戻せる。
- 文字の色は対象外（9.2）。パネルを明るい色にすると白い文字が読みにくくなるため、暗い配色の範囲で色味を変える使い方を想定している。

## 10. 部品と Udon の連携（SYS-01・SYS-02）

### 10.1 イベント連携（SYS-01）

操作できる部品には、部品ごとの専用スクリプトを持たせる。制作者は部品の「通知先」と「イベント名」の2欄を設定する。部品は操作されると、通知先の Udon にそのイベントを送る。

制作者側のスクリプトの例（部品名やメンバー名は例で、実装時に確定する）：

```csharp
public class LampSwitch : UdonSharpBehaviour
{
    public ToggleSwitch toggle;   // ツールキットの部品
    public GameObject lamp;

    public void OnLampToggled()   // 部品の「イベント名」欄に書いた名前
    {
        lamp.SetActive(toggle.IsOn);
    }
}
```

採用しなかった案：Unity 標準のイベント欄に制作者が直接設定する方式。Udon は増えないが、設定手順が煩雑で間違えやすく、見た目の制御や効果音を別に用意する必要がある。

### 10.2 値の取得と設定（SYS-02）

| 操作 | 方式 |
|---|---|
| 取得 | 通知は「変わった」ことだけを伝える。値は部品に問い合わせて読む |
| 設定 | `SetValue(値)` で変更する。通知を出さずに変える `SetValueWithoutNotify(値)` も用意する（初期化や同期で通知が循環するのを防ぐ） |

| 部品 | 値の型 |
|---|---|
| トグルスイッチ | 真偽 |
| スライダー | 小数 |
| 選択ボタン群 | 番号（整数） |
| チェックボックス | 真偽 |
| 数値ステッパー | 小数 |
| 進捗バー | 小数（0〜1）。読み書きだけで、通知は無い |

通知と同時に値を通知先へ書き込む方式は、設定欄が増えるため第1段階では見送る。

### 10.3 共通ルール

- 共通の親スクリプトを1つ作り、通知先・イベント名・通知処理をまとめる。
- 部品の内部で使うイベント名は `_` で始める。VRChat ではこの形の名前はネットワーク経由で呼べないため、外部からの不正な呼び出しを防げる。
- 部品の状態は uGUI 側（Toggle、Slider）の1か所だけで持ち、部品のスクリプトを通して読み書きする。スクリプトにも持たせると二重管理になり、エディタで設定した初期値と食い違うおそれがあるため。数値ステッパーだけは、対応する uGUI の部品が無いので、スクリプトが値を持つ。
- 毎フレーム動く処理は持たない（NFR-01）。
- 部品1つにつき Udon が1つ増えるが、待機中の処理は持たないため負荷は小さい。

### 10.4 ウィンドウの開閉（LAY-02）

ウィンドウのスクリプト（`WindowPanel`）は、次の操作を持つ。ボタンの通知先にウィンドウを、イベント名に操作の名前を設定すれば、制作者がスクリプトを書かずに開閉できる。

| 操作 | 内容 |
|---|---|
| `Open` | 開く |
| `Close` | 閉じる |
| `ToggleOpen` | 開いていれば閉じ、閉じていれば開く |
| `IsOpen` | 開いていれば真（スクリプトから読む） |

- 閉じると Canvas ごと無効になり、当たり判定も消える。見えないウィンドウがレーザーを遮らない。
- 開閉が変わると、他の部品と同じく通知先にイベントを送る。
- `WindowPanel` は Canvas の親に置く。閉じている間も常に有効な場所にあるので、初期化（`Start`）が開閉に左右されない。
- 制作者側のスクリプトも、ウィンドウの外に置くことを勧める。ウィンドウの中に置くと、最初に開くまで `Start` が実行されないため。

**一度も有効になっていないオブジェクトの Udon の動き**（2026-10-12 に確認）

以前は「一度も有効になっていないオブジェクトの Udon は、イベントを受け取れない」と考えていたが、誤りだった。試験用のシーン（最初から閉じているウィンドウの中の部品を、外のスクリプトから読み書きする）を作り、Unity 上の再生と PC の VRChat で確かめた。SDK のコード（`UdonBehaviour.cs`）とも合っている。

| 種類 | 一度も有効になっていない状態での動き |
|---|---|
| ほかのスクリプトからの呼び出し、`SendCustomEvent` による通知 | 実行される。値の読み書きも、そこからの通知も動く |
| `Start` | 最初に有効になるまで実行されない |
| VRChat が呼び出すイベント（`OnPlayerJoined`、`Interact` など） | `Start` が済むまで実行されない |

- 部品のスクリプトは、`Start` が済んでいなくても正しく動くように作る。`Start` でしか行わない準備に頼らない（例：`SegmentedControl` は、最初に使われたときに準備する）。
- タブの表示していないページや、閉じているダイアログの中の部品も、この前提で読み書きできる。
- Quest では未確認。Udon の仕組みは PC と同じなので、同じ動きになる見込み。
- 試験用のコードは `Assets/ZSTests/` にある（git では管理しない）。

## 11. 配置の仕組み（LAY-02・LAY-04・EDT-01）

部品を置くだけで整列するように、次の仕組みにしている。

### 11.1 中身の領域

- ウィンドウ（`ZS_Window`）と、パネルつきの Canvas（`UIBuilder.CreatePanelCanvas`、メニューの「Canvas とパネル」）は、`Content` という名前の中身の領域を持つ。
- 中身の領域は縦の自動配置で、置いた部品は上から順に並ぶ。位置の指定は要らない。
- 中身の領域の高さを超えると、下にはみ出す。スクロールは LAY-06 で扱う。

### 11.2 縦の自動配置での幅の扱い

各プレハブが、uGUI 標準の `LayoutElement` で幅の方針を持つ。高さは各部品の値をそのまま使う。

| 幅の方針 | 対象 |
|---|---|
| 幅を保ち、左に寄せる | ボタン、アイコンボタン、トグルスイッチ、数値ステッパー、アイコン |
| 枠の幅いっぱいに広がる | 設定行、チェックボックス、スライダー、選択ボタン群、進捗バー、ラベル、自動配置（縦・横） |

- `LayoutElement` を持たない要素（ツールキット以外のオブジェクトなど）は、縦の自動配置の中で幅が 0 になる。入れる場合は `LayoutElement` を付ける。
- 幅を保つ部品の幅を変えるときは、`UIBuilder.SetSize` を使う（`LayoutElement` の値も合わせて書き換える）。
- 横の自動配置は、子の大きさを変えずに左から並べる。

### 11.3 自由に配置したい場合

Canvas やパネルの直下に置いた部品は、親の中央が基準になる。位置は `UIBuilder.Place` か、Unity 上での移動で決める。

### 11.4 メニューから追加するときの決まり（EDT-01）

- 部品は、選択中のオブジェクトの下に置く。
- ウィンドウか、中身の領域を持つ Canvas を選んでいる場合は、中身の領域に置く。
- 設定行を選んで操作部品を追加した場合は、行の右端に寄せて置く。
- Canvas の外で部品を追加した場合は、パネルつきの Canvas を自動で作り、その中身の領域に置く。
- ウィンドウと Canvas は、別の Canvas の中には作らない。Canvas の中に作ると縮尺が二重に掛かり、見えない大きさになるため。その場合はシーンの最上位に作る。

## 12. フォント（FND-06・EDT-06）

### 12.1 方式

- ツールキットのラベルは、すべて共通のフォントアセット `Runtime/Fonts/ZS_Font.asset` を使う。
- フォントを変えるときは、このアセットの中身を別のフォントから作り直す。アセット自体は同じものなので、プレハブも配置済みの UI も、手を加えずに新しいフォントに切り替わる。
- **フォントは同梱しない。** 配布物と git には、中身が空の `ZS_Font` だけを含める。中身は利用者の環境で生成する。こちらからフォントを再配布しないので、配布物についてのライセンス上の義務が軽くなる。

| 段階 | 状態 | 利用者の操作 |
|---|---|---|
| 導入直後 | `ZS_Font` は空。文字は TextMeshPro の既定のフォントで補われて表示される | なし |
| プロジェクトを開いたとき | 利用者の手元にある TextMeshPro 標準のフォント（LiberationSans）から、英数字と記号を自動で生成する | なし（自動） |
| 日本語を使いたいとき | Noto Sans JP を取得し、常用漢字までを生成する | 「フォント設定」で「Noto Sans JP をダウンロード」と「生成」を押す |
| ツールキットを更新したとき | `ZS_Font` は空に戻る。前回の生成と同じフォントと画像の大きさで、自動で生成し直す（8.7） | なし（自動） |

### 12.2 収録する文字

- かな、英数字、記号（一部は範囲を丸ごと指定している。元のフォントに無い文字は自動で除かれる）
- 常用漢字 2,136 字（Unicode の漢字データベースから抽出）と、よく入力される異体字4字（剥・叱・填・頬）
- 「フォント設定」の「追加で収録する文字」に書いた文字
- 範囲外の文字は、VRChat が持つ文字の補完の仕組みに任せる。エディタ上では □ になる。
  - Quest 3 と PC の VRChat で、範囲外の文字（薔薇、檸檬、醤）が表示されることを確認済み（2026-10-12）。デモシーンの「Japanese」の2行目が、その確認用の表示例。
  - 補完が働く条件は、プロジェクト設定の TextMeshPro の「Fallback Font Assets」が空であること（VRChat の公式ドキュメントによる）。このプロジェクトは最初から空だった。空でないプロジェクトで使う利用者には、導入手順書（DST-02）で案内する。

Noto Sans JP を 4096 x 2048 の画像で生成した場合、収録は 2,732 文字、文字の大きさは 46、メモリは約 8MB になる。文字の大きさは、画像に全部の文字が収まる範囲で自動的に最大にする。

### 12.3 Noto Sans JP の取得

- 「フォント設定」のボタンを押したときだけ、Noto フォントの公式リポジトリ（GitHub の `notofonts/noto-cjk`）から、フォントとライセンス文書を取得する。
- 入手元の内容が後から変わっても同じファイルを取得できるよう、特定の版を指定している。取得した内容は、想定したものと一致するかを照合してから保存する。
- ライセンスは SIL Open Font License 1.1。生成したフォントアセットは元のフォントの改変版にあたり、同じライセンスが適用される。ワールド制作者には、ワールド内か説明欄にフォント名とライセンスを記載するよう、導入手順書（DST-02）で案内する。
- 取得したフォントとライセンス文書は `Assets/ZeroShotUdonUI/Fonts/` に置く。パッケージの外なので、ツールキットを更新しても消えない。git の管理対象外にしている。

### 12.4 開発時の注意

- **`ZS_Font.asset` は空の状態で git に記録している。** 手元で生成した中身（約 18MB）が誤って記録されないよう、このファイルの手元での変更を git が無視する設定（skip-worktree）をしている。
- 空の状態の内容を更新したいときは、「フォント設定」の「空の状態に戻す」を押してから、設定を一時的に解除して記録する。
- 配布物を作る前にも、「空の状態に戻す」を押す。
- 中身を入れ替えた後は、そのフォントを使うシーン上の文字を作り直す必要がある（`FontGenerator.RefreshTexts`）。文字の描画データが画像上の位置を覚えているためで、作り直さないと表示が消えたり崩れたりする。

## 13. アイコン（FND-07・CMP-02）

### 13.1 方式

- アイコンは画像を使わず、シェーダー（`Runtime/Shaders/Icon.shader`）が線で描く。導入直後から使え、どの大きさでも輪郭が鮮明になる。
- マテリアルは `ZS_Icon` の1つだけ。アイコンの種類は、部品（RawImage）の UV Rect の X に「種類の番号 × 2」を入れてシェーダーに伝える。種類ごとにマテリアルを増やさずに済む。
- 要素の短辺に合わせた正方形の中に描くので、大きさを変えても形は崩れない。線の太さは、マテリアルの値（短辺に対する割合）で決まる。
- 色は部品ごとに持つ（RawImage の Color）。文字と同じ扱いで、テーマ（9章）の対象外。

### 13.2 種類

番号は、`UIBuilder` の `IconType` の並び順と、シェーダー内の番号で対応している。

| 番号 | 名前 | 形 |
|---|---|---|
| 0 | `Close` | × |
| 1 | `Check` | チェック |
| 2 | `Plus` | ＋ |
| 3 | `Minus` | － |
| 4〜7 | `ChevronUp`・`ChevronDown`・`ChevronLeft`・`ChevronRight` | 矢印の先（上・下・左・右） |
| 8 | `Menu` | 三本線 |
| 9 | `Info` | 丸に i |

### 13.3 使い方と追加の仕方

- コードからは `UIBuilder.CreateIcon`、`UIBuilder.CreateIconButton` で置く。種類は `UIBuilder.SetIcon` で後から変えられる。
- Udon からも、RawImage の UV Rect を書き換えれば種類を切り替えられる（必要な機能が Udon に公開されていることを確認済み）。
- 種類を追加するときは、`IconType` の末尾に名前を足し、シェーダーの `IconDistance` に同じ番号で形を足す。途中に挿入したり順番を入れ替えたりすると、配置済みのアイコンの種類がずれる。
- 歯車のような複雑な形は、この方式では作りにくい。種類を大きく増やしたくなった場合は、アイコン用フォントを利用者が取得する方式を検討する（Q-04）。
